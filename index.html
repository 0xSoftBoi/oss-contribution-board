alloy #4162 — heartbeat receipt recheck

Push the follow-up

alloy-rs/alloy · fix(provider) · opened against issue #3881

The PR is sound and its four tests pass. But it still hangs in the exact scenario the issue reports — a server whose eth_blockNumber is stale and never catches up — because the recheck asked that same stale server for the height. A receipt in block n already proves the chain is at least n blocks long, so the receipts can supply the height themselves.

Wrote a failing test for that case against your branch, confirmed the hang, then confirmed it passes after the fix. The eth_blockNumber request is now gone entirely — one fewer RPC call per cycle, and the block stream already polls it.

In the patch

  • Chain height derived from receipts, so a single-confirmation watcher resolves even when the reported height is frozen.
  • Dropped the redundant eth_blockNumber call from every recheck cycle.
  • Next recheck is scheduled when the previous result lands, not when it is spawned — a slow recheck no longer triggers the next one back-to-back.
  • RecheckResult collapses to a plain vector; the recheck task always replies, so the loop can't get stuck with recheck_running set.

parse_datetime #286 — 8j rejected

Close it, open the real fix

uutils/parse_datetime · open since 5 Apr · changes requested 5 Jul

sylvestre was right, and it is worth knowing exactly how right. I ran GNU coreutils 9.4 across the whole alphabet: every letter a–y is a military time zone, and all of them are already in your table. j is the single missing entry — and it's missing because it's the one letter that means local time rather than an offset, so it can't be expressed as an Offset at all.

date -d '8a' → 07:00 UTC (UTC+1) · date -d '8n' → 09:00 UTC (UTC−1) · date -d '8j' → identical to date -d '8' · date -d '8foo' → invalid date. GNU does not discard unknown tokens, which is what #286 assumed.

In the patch

  • j parsed as its own item — local time, no offset — so 8j, 8 j and 8J all work.
  • Still counts as a time zone item: 8j utc, 8 utc j and 8 j j are rejected as a repeated zone, matching GNU.
  • Consumes the whole alphabetic word before comparing, so 8jan still parses as a date.
  • Unknown words stay errors. 8foo fails, as it does in GNU.

Next#286 is now five months behind main and its diff reverts three later fixes, including your own am/pm change. Close it with a note, open a fresh 105-line PR from the patch, and quote the GNU 9.4 letter table in the body — sylvestre gets to see his review was acted on precisely.

What the ledger says about where to spend time

Six of your PRs were superseded by someone else's — all in one repo

#1360, #1362, #1365, #1366, #1368 and #1370 were all overtaken by a parallel PR fixing the same thing. That is what a high-traffic repo with a slow review queue does to small independent fixes: several people find the same bug, and the one that gets merged is whichever the maintainer happens to open first.

The counter is not to write more of them. It is to comment on the issue before opening the PR — one line claiming the fix — so a maintainer merging someone else's work at least sees yours first. #1362 is the proof it works: soobrosa folded your flags into #1353 and credited you.

parse_datetime and coreutils merged five of your six PRs. They are slow — #284, #285 and #287 all sat three months before landing together on the same day — but they land, and sylvestre reviews substantively rather than triaging down.
